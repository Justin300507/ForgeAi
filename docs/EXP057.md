# Experiment 057 — Restore Runtime Repair Loop (targeted regression fix)

2026-07-12. Direct follow-up to Experiment 056's baseline measurement,
which found and root-caused (but explicitly did not fix, per its own
"measurement only" rule) a regression from Experiment 053 (commit
`f7d4dca`). This experiment fixes exactly that regression and nothing
else.

## Root cause

`app/services/v6_orchestrator.py`'s `generate_project_v6` has a runtime-fix
retry loop (Stage 12, `for r_attempt in range(max_runtime_attempts + 1)`,
`max_runtime_attempts = 3` — up to 4 validate→fix→re-clean cycles). On
each iteration where a fix is needed, it calls 5 database-shape cleanup
patchers bare: `patch_model_field_mismatches`,
`patch_add_missing_model_columns`, `patch_add_missing_schema_fields`,
`patch_missing_required_constructor_kwargs`,
`patch_filter_dict_unpack_constructor_kwargs`.

**Before Exp053**, `generate_project_v6`'s own Stage-1 code (near the top
of the function) did:
```python
from app.services.database_patcher import (
    patch_database_py, patch_model_field_mismatches, patch_add_missing_model_columns,
    patch_add_missing_schema_fields, patch_missing_required_constructor_kwargs,
    patch_filter_dict_unpack_constructor_kwargs,
)
```
Python function-local imports bind for the *rest of the enclosing
function's execution*, not just the following lines — so this import
stayed in scope for the Stage-12 loop ~500 lines later, in the same
function.

**Exp053** (`git show f7d4dca`) extracted that Stage-1 code, import
included, into a new helper function, `_run_initial_deterministic_patches()`,
to deduplicate it against `repair_project()`'s near-identical Stage 1.
That import is now scoped to the helper only. Stage 12's bare calls,
still in `generate_project_v6`'s own body, were never updated — they
silently became unbound-name references.

**Confirmed as a genuine regression, not a pre-existing bug:** Exp053's
own test suite passed because nothing in it exercised the Stage-12 loop;
the bug surfaced only in Exp056's live canary run, where the loop's own
`try/except Exception as re_err:` (line ~861, pre-existing, untouched by
Exp053) caught the `NameError` and recorded it as
`runtime_result = {"success": False, "error": "name 'patch_model_field_mismatches' is not defined"}`
instead of crashing the pipeline — which is exactly why it went unnoticed
until a real generation run hit it.

## Fix

**Task 1 — correct scope:** the correct scope is `generate_project_v6`'s
own body, specifically the `if validation["passed"]:` block that already
contains a *working*, correctly-scoped import for one of the six
needed names:
```python
from app.services.database_patcher import patch_database_py
patch_database_py(project_path)
```
This import already stays in scope through Stage 12 — proven by
`patch_database_py`'s own bare call inside the loop (line ~846) never
raising a `NameError`. That's the correct scope for the other 5 names
too.

**Task 2 — restore visibility without duplicate imports:** the fix
widens that *existing* import statement to include the 5 missing names,
rather than adding a second, new import statement anywhere:
```python
from app.services.database_patcher import (
    patch_database_py, patch_model_field_mismatches, patch_add_missing_model_columns,
    patch_add_missing_schema_fields, patch_missing_required_constructor_kwargs,
    patch_filter_dict_unpack_constructor_kwargs,
)
patch_database_py(project_path)
```
This is a **5-line diff** (one import statement widened from 1 name to
6, plus an explanatory comment). Nothing else in the file changed.
`_run_initial_deterministic_patches()`'s own separate import (needed for
its own, independent execution) was left untouched — it is a different
scope with a genuine, independent need for the same names, not a
duplicate of this fix.

Not done, deliberately: no refactor of the other 5 pre-existing
`patch_database_py`-only local imports elsewhere in this same file
(lines ~483, ~667, ~1192, ~1200) — those are unrelated call sites,
untouched by Exp053, not broken, and touching them would violate this
experiment's own "do not refactor unrelated code" rule. No change to
`repair_project()` — it doesn't contain this loop pattern at all
(confirmed: `patch_model_field_mismatches(project_path)` appears bare
only inside `generate_project_v6`, nowhere in `repair_project`).

## Evidence

**Task 3 — verify all retry iterations execute**, and **Task 4 —
regression tests**: `tests/reliability/test_runtime_fix_loop_scope.py`,
7 tests, two layers:

1. **Structural** (against the real, current source via
   `inspect.getsource`, not a hand-copied reproduction):
   - the widened import contains all 5 previously-missing names
   - exactly one `database_patcher` import exists in the Stage-12 block
     (no duplicate introduced)
   - `_run_initial_deterministic_patches` still exists, still has its
     own separate import, still gets called from Stage 1 — helper
     extraction is intact, not undone
   - exactly 4 occurrences of `patch_model_field_mismatches` remain in
     the whole file (helper import + helper call + Stage-12 import +
     Stage-12 call) — no accidental third copy

2. **Functional** (executes the *real* extracted Stage-12 source in a
   controlled harness — not a hand-copied reimplementation of the loop's
   logic, so it can't silently drift from the real code):
   - `test_no_name_error_and_all_iterations_execute_when_always_failing`:
     `validate_runtime` always fails → all 4 intended calls happen
     (`range(max_runtime_attempts + 1)`), all 5 cleanup patchers run on
     each of the 3 non-final iterations, no exception
   - `test_no_name_error_with_success_on_third_attempt`: fails twice
     then succeeds → loop breaks immediately on success, exactly 3
     `validate_runtime` calls, exactly 2 fix-and-clean cycles
   - `test_stagnation_guard_still_stops_early_unchanged`: identical
     failure signature every time → the **pre-existing, untouched**
     stagnation guard still stops the loop after 2 calls (1 fix
     generated) — proving Exp057 changed *only* the import, not the
     retry-termination logic

**Task 5 — replay the failing scenario from Exp056**, via `git stash`
(the same before/after verification pattern used in Exp054/055):
stashed the fix, re-ran the exact "always failing" scenario against the
unmodified pre-Exp057 code. Result — **an exact match to Exp056's real
canary logs**, not just "some error occurred":
```
runtime_result = {'success': False, 'error': "name 'patch_model_field_mismatches' is not defined"}
```
`validate_runtime` was called **1 time**, not 4 — the loop's own
`try/except` swallowed the `NameError` on the very first fix-and-clean
attempt, exactly as the Stage-12 code does, exactly as the real Exp056
canary logs showed. Popped the stash, re-ran the same scenario against
the fixed code: all 4 `validate_runtime` calls happen, no error field,
7/7 tests green.

Full existing suite (48 test files, up from 47 — this experiment's own
new file) plus `tests/adr002/test_orchestrator_wiring.py` re-run and
confirmed passing before and after.

## Before / after behavior

| | Before (Exp053-056) | After (Exp057) |
|---|---|---|
| Stage-12 loop iterations on a persistently-failing app | 1 (crashes on first fix-and-clean attempt) | up to 4, as designed |
| `runtime_result` on a persistent failure | `{"success": False, "error": "name 'patch_model_field_mismatches' is not defined"}` (masks the real runtime error) | the real `validate_runtime()` failure detail from the final attempt |
| `Runtime Fixes` LLM-call count (Exp056's independent corroborating signal) | stuck at 1 regardless of `max_runtime_attempts` | scales with actual failed attempts, up to `max_runtime_attempts` |
| Success-breaks-immediately behavior | unchanged (never reached — always crashed first) | unchanged, verified working |
| Stagnation guard | unchanged (never reached) | unchanged, verified working |
| `_run_initial_deterministic_patches` helper (Exp053's extraction) | present | present, untouched |
| Other 5 `patch_database_py`-only local imports elsewhere in the file | present | present, untouched |

## Cost

$0. No generation, no LLM calls, no prompt changes — pure Python scoping
fix backed by direct reproduction (both the original failure via
`git stash` and the fix's correctness), matching this project's
established $0-first methodology for regression fixes with a known exact
root cause.

## What Exp056's baseline predicted this should recover

Not re-validated via a live canary this cycle (would cost real API
credits; the fix's correctness was proven via the exact-replay harness
above, which is a stronger, cheaper, more targeted signal than a fresh
3-app run for a scoping fix this precisely diagnosed). A future cycle
with canary budget should re-run the same todo/blog_cms/crm canary and
confirm the Stage-12 loop actually recovers `Runtime Startup` on at
least some of the previously-stuck attempts — Exp056's own report
flagged this as the natural next re-measurement point.
