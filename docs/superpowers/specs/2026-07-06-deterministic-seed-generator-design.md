# ADR-002 Candidate: Deterministic Reference-Data Seeder — Design

**Status**: Approved for implementation (pending benchmark confirmation before promotion to ADR-002)
**Date**: 2026-07-06
**Scope**: `v6_orchestrator.py`'s missing-`seed_routes.py` fallback path ONLY. The primary
LLM-authored seed prompt (`shared_contract.py`) is untouched.

## Problem

When the LLM omits `app/routes/seed_routes.py` entirely, `v6_orchestrator.py` (line ~448)
writes a static 4-line stub that returns `{"seeded": True}` without inserting any rows. Any
entity with a required FK to a lookup/reference table (e.g. todo's `Task.priority_id` →
`priorities`) then fails Create with a 400, because the lookup table is permanently empty.
This has recurred in every todo canary run this cycle (Experiments 013, 015-019) and is
gated purely by whether the LLM happened to produce a real seed script that attempt — a
coin flip, not a fix.

## Root cause

Not a generation defect — a test/repair-infrastructure gap. The fallback stub was
deliberately written to never call the LLM (confirmed in code comments: the LLM has no
project context in this repair branch and previously invented wrong-domain data, e.g.
gym/hospital records, for unrelated apps). That constraint was correctly conservative but
left the stub a pure no-op instead of doing anything structurally useful.

## Core philosophy (extends ADR-001)

> Whenever multiple LLM generations would otherwise need to independently agree on the same
> information, replace that agreement with one deterministic artifact generated once and
> reused everywhere.

ADR-001 applied this to model→schema field-name agreement via `entity_metadata.py`. This
design applies the same principle to model→seed-data agreement:

```
ADR-001:  Model -> Entity Metadata -> Schema
ADR-002:  Model -> Entity Metadata -> Deterministic Seeder
```

## Architecture

New module: `backend/app/services/deterministic_seed_generator.py`. Built entirely on the
existing `entity_metadata.py` (Experiment 017) — no parsing logic is duplicated or added to
that module.

### Components

- `discover_models(project_path) -> dict[str, EntityDefinition]`
  Scans `app/models/*.py` on disk, parses each with the existing
  `extract_entity_definition()`. Files that parse to `None` (re-export shims) are skipped.
  The `users`/`user` table is excluded unconditionally (structural rule: any entity whose
  parsed `table_name` is `users` or `user`).

- `find_lookup_entities(entities) -> list[EntityDefinition]`
  Structural FK-target heuristic only: build the set of every table name that appears as an
  FK target (`fk_target.split(".")[0]`) across all discovered entities; an entity qualifies
  as a lookup entity iff its own `table_name` is in that target set. No entity-name
  keyword-matching anywhere (no "Priority", "Category", "Status" special-casing).

- `topological_order(entities) -> list[EntityDefinition] | None`
  Kahn's algorithm over the FK subgraph restricted to the lookup set. Returns `None` if a
  cycle is detected (not every node consumable) — the caller treats `None` as "abort,
  fall back to static stub," logging `"FK cycle detected"`. No partial-ordering attempt.

- `generate_field_value(field: FieldDefinition, row_index: int, class_name: str) -> str`
  (returns a Python source literal, not a runtime value)
  Purely type-driven, zero semantic guessing:
  - `String`/`Text`/`Unicode`-family → `f"{class_name} {row_index + 1}"`
  - `Integer`/`Numeric`/`Float` → `row_index + 1`
  - `Boolean` → alternate `True`/`False` by `row_index % 2`
  - `Date`/`DateTime` → `datetime.utcnow() - timedelta(days=row_index)`
  - `Enum` → the string fallback above (`f"{class_name} {row_index + 1}"`) — no attempt to
    read the enum's actual member values, since that would require deeper parsing beyond
    `entity_metadata`'s current scope
  - `UUID` → `str(uuid.uuid4())` (random but valid — a real UUID has no "deterministic
    literal" that means anything, so the determinism guarantee here is "always a
    well-formed unique value," not "always the same value")
  - Anything else, if not nullable → the string fallback above (never leave a NOT NULL
    column unset)
  FK columns whose target is NOT in the lookup set (e.g. an optional `owner_id -> users.id`)
  are rendered as a runtime lookup: `db.query(User).first()`, and the row insert is skipped
  entirely (wrapped) if that returns `None`.

- `render_seed_routes(entities_in_order: list[EntityDefinition]) -> str`
  Emits the complete `seed_routes.py` source:
  - A version header comment block:
    ```python
    # Generated by ForgeAI Deterministic Seeder
    # ADR-002
    # Generator Version: 1
    # Timestamp: <ISO8601 at generation time>
    ```
  - One `_seed_<table_name>(db)` helper per lookup entity, count-gated (see Idempotency)
  - The `POST /seed` handler, calling each helper in topological order, returning a
    structured summary (see Telemetry / Response Shape)

### Wire-up

`v6_orchestrator.py`'s existing fallback branch calls
`deterministic_seed_generator.generate(project_path)` instead of writing the static
template directly. Any exception, or a `None`/empty result (no lookup entities found, or a
cycle detected), falls back to writing today's exact static stub — this path must never
cause seed_routes.py generation to fail outright.

## Idempotency — count-based (not field- or constraint-based)

```python
TARGET_ROWS = 3

def _seed_<table>(db: Session) -> dict:
    existing = db.query(<Model>).count()
    if existing >= TARGET_ROWS:
        return {"inserted": 0, "skipped": TARGET_ROWS, "already_existed": existing}
    inserted = 0
    for i in range(existing, TARGET_ROWS):
        try:
            db.add(<Model>(...deterministic literals...))
            db.commit()
            inserted += 1
        except IntegrityError:
            db.rollback()
    return {"inserted": inserted, "skipped": TARGET_ROWS - existing - inserted,
            "already_existed": existing}
```

**Why count-based, not field-guess or UNIQUE-constraint-based**: the objective is
deterministic *fallback infrastructure*, not business-level deduplication. A field-based
"identifying column" guess (e.g. assuming the first non-FK required field is a natural key)
is fragile across arbitrary schemas. A `UNIQUE`-constraint-based check is strictly correct
only when such a constraint exists — most LLM-generated lookup tables don't declare one,
which means `IntegrityError` would never fire and rows would silently duplicate on every
repeat `POST /seed`, violating the idempotency requirement outright.
`db.query(Model).count() >= TARGET_ROWS` needs nothing beyond what `entity_metadata`
already parses (`table_name`), is trivially idempotent by construction (second call always
sees `count >= 3` and returns immediately), and requires zero expansion of
`entity_metadata.py`. The per-insert `try/except IntegrityError/rollback` is kept as
defense-in-depth only — correctness never depends on it firing.

## Lookup entity detection & exclusions

FK-target heuristic only (see above). Explicitly never seeded, by construction (not by
name-matching):
- `users` / authentication entities (excluded by table-name check)
- The main CRUD-journey target entity and any other entity with zero incoming FK references
  (never appears in the lookup set because nothing points to it)
- Any entity requiring business-meaningful data (customers, products, blog posts, invoices,
  tasks) — these are out of scope by definition, since the FK-target heuristic only
  surfaces entities that exist purely to be referenced by others, i.e., reference/lookup
  tables. The generator has no code path that could produce business data even if a
  business entity happened to have an inbound FK from another business entity — the row
  values are always the generic typed placeholders in "Data" below, never domain content.

## Data generation

Exactly 3 rows per lookup entity. Values generated only from parsed type information —
string, numeric, boolean, date/datetime, UUID. No semantic guessing, no keyword-based value
banks (e.g. no hardcoded `["Low", "Medium", "High"]` for anything resembling "priority" or
"level" — this was explicitly rejected in favor of the fully mechanical approach).

## Fallback conditions (any one triggers immediate fallback to today's static stub)

- No models discovered / unreadable `app/models/` directory
- Zero lookup entities found (a schema with no reference tables, e.g. no FK targets at all)
- FK cycle detected in the lookup subgraph
- Any exception during discovery, ordering, value generation, or rendering

Generation must never fail because deterministic seeding failed — the static stub is always
the safety net, and today's baseline behavior is the floor, never the ceiling.

## Telemetry

At codegen time (inside `v6_orchestrator.py`, when this fallback fires), log:
- ADR-002 path enabled (vs. static-stub fallback used)
- Entities discovered (count)
- Lookup entities (count)
- Fallback used (bool) and reason if so (`"no lookup entities"` / `"FK cycle detected"` /
  exception message)
- Generation time (ms)

At runtime (when the generated `POST /seed` endpoint actually executes — captured by
`user_journey_runner.py`'s existing best-effort `/seed` call), the response body is
extended with structured per-entity counts (`inserted`, `skipped`, `already_existed`) so
this data is visible in the journey's own telemetry record without adding a new capture
mechanism. Exact wiring into `generation_log.jsonl` is an implementation-planning detail,
not fixed here.

## Testing plan (all local, $0, before any canary)

Unit tests against fixture model-file strings (no server, no LLM):
1. No lookup entities (schema with no FK targets at all) → generator returns `None`/falls
   back
2. Single lookup entity, no FK chain
3. Multiple independent lookup entities
4. Multi-level FK chain (lookup entity FKs another lookup entity) → correct topological
   order
5. FK cycle among lookup entities → detected, aborts, falls back
6. Nullable FK to a non-lookup entity (e.g. optional `owner_id`) → runtime-lookup rendering
   correct
7. Repeated `POST /seed` semantics (simulate count-based logic directly): first call
   inserts 3, second call inserts 0
8. Pre-existing data: entity already has 1-2 rows before first `/seed` call → generator
   tops up to `TARGET_ROWS`, not additive beyond it
9. Broken/malformed model file → `extract_entity_definition` returns `None`, handled
   gracefully (already proven behavior from Experiment 017, exercised here in this new
   caller)
10. Empty project (no `app/models/` directory) → fallback, no crash
11. Generated `seed_routes.py` source parses cleanly (`ast.parse`) for every fixture
    scenario above that produces output

## Benchmark plan (only after all local tests above pass)

`run_canary.py`, fixed 3-app suite (todo / blog_cms / crm), `--no-deploy`. Collect: Runtime
success, CRUD/Journey pass rate, repair-attempt count, seed telemetry (lookup entities
found, rows inserted/skipped, fallback-used rate), generation cost (should be unchanged —
zero new LLM calls), Forge Score, and run-to-run variance. Compare against Experiment 019's
entry in `canary_history.json`.

**Judge by** (per project convention — do not judge by Forge Score alone):
- Did CRUD reliability improve (specifically: does todo's Create-entity 400 disappear
  regardless of whether the LLM produced a real seed script that attempt)?
- Did repair-attempt count decrease or stay equal?
- Did reference-table-related failures decrease?
- Does telemetry confirm the deterministic path actually executed (not silently falling
  back every time)?

## Acceptance criteria

- CRUD reliability improves (or at minimum, todo's specific gated failure disappears)
- Reference-table failures decrease
- No new deterministic regressions appear in blog_cms/crm
- Repair count decreases or stays equal
- Runtime success remains stable
- Benchmark variance does not increase
- Telemetry confirms deterministic seeding executed correctly when it should have

## Explicitly out of scope (this cycle)

- Redesigning or touching the primary LLM-authored `seed_routes.py` prompt path
  (`shared_contract.py`) — untouched
- Relationship/secondary-table (`relationship()`, many-to-many) seeding
- Composite lookup entities (multi-column natural keys)
- Enum-type extraction (SQLAlchemy `Enum` columns treated as a plain string type for now)
- Advanced deterministic defaults beyond the basic type-driven set above
- Adding `unique=True` parsing to `entity_metadata.py` (not needed — count-based
  idempotency requires nothing beyond `table_name`)

These are listed as candidate future extensions in ADR-002 once written, not implemented
now.
